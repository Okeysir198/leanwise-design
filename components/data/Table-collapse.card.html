Tables on phones

base.css alone. This card loads no product layer on purpose: .lw-table, the wrap, the cards and the hint are all base, and a specimen that loads more than its documented recipe cannot measure the recipe. The one thing it therefore cannot show is the open Sort panel — Menu paints on .lw-popover, which is product.css. That is a real caveat of the pattern, and it is stated in Table.d.ts rather than papered over here.

The width that matters is the container's, not the screen's. The two panes below are the same component with the same props on the same page, at the same viewport. The first is 360px wide — a phone, or the 318px track a console list actually gets inside a rail — and every row is a card. The second is wide, and it is a table with its header row and its sort buttons. Nothing measured anything in JavaScript to decide that; @container lw-table (max-width: 767.98px) did, off the wrapper's own inline size.

why it is built this way

One DOM, two layouts

The markup does not change at the breakpoint. It is one real <table> at every width, re-laid-out by CSS — so nothing is measured, nothing re-renders, and the server and the client cannot disagree about which form to emit. Re-rendering a card list below 768px is the obvious alternative and it costs the table its semantics, its column headers and its keyboard the moment the JavaScript is late.

The price is stated rather than hidden: display: block on a table element drops the implicit table semantics in every engine, so Table emits explicit role="table" / "rowgroup" / "row" / "columnheader" / "cell" whenever collapse is set — and only then, so a table that does not collapse keeps the markup it has always had, byte for byte.

First cell, next two, then the rest

Three is not arbitrary. A card read at a glance carries one strong line and one weak one; everything past that is detail by definition. So the first cell titles the card, the next two are its meta line, and the remainder sit behind a native <details> whose label the consumer supplies — "Chi tiết", "Details", "Detalles". This package holds no display text, which is why detailsLabel is required in the type the moment collapse is set rather than defaulted to an English word.

The disclosure holds the control, not the cells, and that is forced rather than chosen: a <details> wrapping <td>s is not expressible, because the HTML parser foster-parents any non-cell child of a <tr> straight out of the table. The summary rides in the title cell and tr:has(.lw-row-more[open]) reveals the siblings that follow it.

Each detail cell prints its own column name from data-label, because the header row is gone. Hiding that row with display: none rather than visually — the tempting choice — is deliberate: a visually-hidden header stays in the accessibility tree and in the prefix, so every cell would announce its column twice.

Sorting survives the collapse

Collapsing hides the header row and with it every sort button, so the sortable columns are re-offered through Menu — the component that already owns roving focus, typeahead and Esc here. The active column is a menuitemcheckbox, so which way the list is sorted is announced rather than being a caret a screen reader never reaches, and choosing it again flips the direction. The trigger is a real .lw-btn; sort the narrow pane and the wide one does not move, because they are two independent roots, which is the point of showing both.

The hint, for every table that has not migrated

A wrap has scrolled sideways since v1.7.0 and never said so. Below is the same table with no collapse at all, in a track too narrow for it — six console lists ship in exactly this state, 1.5–2.4× the viewport wide, with the scrollbar as the only affordance, and a touch device does not paint one until the finger is already moving.

no collapse — the fade says there is more

The fade is a mask on the wrapper, not a pseudo-element: .lw-table-wrap is the scroll container, so an absolutely positioned ::after resolves against its scrollable area and parks at the far end of the content — 800px off screen. A mask is painted with the element's own box and stays put. It costs the frame's right edge, which reads as the surface running past the edge, which is the message.

One trap worth naming, because this card fell into it first: a .lw-table-wrap inside a grid or flex item needs a min-width: 0 ancestor. The wrap is a scroll container, so it will shrink — but the plain <div> holding it is a grid item with min-width: auto, which is the table's min-content width. The wrap then grows past its pane instead of scrolling, and there is no overflow to hint at: the page scrolls sideways instead, which is the defect one layer up.

It appears only when the wrap actually overflows, and clears the moment the reader reaches the end. A permanent fade is worse than none: it promises content that is not there. The measurement is a ResizeObserver in useOverflow(), and all it does is set data-overflow="true" — so a vanilla consumer with no React sees exactly what it saw before, and anything that can measure its own scroller can set the attribute by hand.
